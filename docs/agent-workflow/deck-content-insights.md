# Deck Content — 인사이트 참고자료 (시스템 설계 고려사항)

> **성격: 규칙이 아니라 참고.** `deck-content.md`가 Phase 3의 규율이라면, 이 문서는 `financial-market` 파일럿(저해상도 콘텐츠 + 근거 검증 + 자산 목록 + 콘텐츠 워크벤치)에서 드러난, **나중에 PPT 제작 시스템을 구축할 때 고려할 것들**을 모은 노트다. 한 사례 기반이라 과적합 위험이 있어 각 항목에 *경계*를 적는다. 규칙과 충돌하면 `deck-content.md`가 우선.

## 파일럿에서 한 일 (요약)

- 슬라이드 메타(`slides/index.js`)에 `body`(저해상도 본문)·`assets`(자산 목록)·`evidence.grade`(근거 강도)를 도입.
- 콘텐츠 워크벤치(`/:sessionId/content`)로 준비도(본문·자산·근거 강도·미검증)와 Phase 4 게이트를 집계.
- 근거 8건의 미검증을 웹 1차 출처 대조로 전부 해소 — **에이전트 자율 검증 4건**(글로벌 시장·PSR 산식·감원 구성·선불 피해) + **시점/재현 의존 4건**(현재 시총·상표출원·유튜버·서울 폐업)을 오늘 기준으로 확정.
- 자산 13개 중 5개만 '확보' — 나머지는 (데이터 확정·작도만 남음 / 출처·라이선스 미확정 / 실물 부재)로 성격이 갈림.

핵심 관찰: **콘텐츠 단계의 진짜 일은 "근거를 1차 출처로 검증하고, 자산의 확보 상태를 정직하게 추적하는 것"이며, 이 중 상당 부분은 에이전트가 조사·제안할 수 있지만 확정·실물 확보는 사람 몫이라 둘의 경계를 시스템이 명시해야 한다.**

## 시스템 설계 고려사항 (일반화)

### 1. 근거 검증을 라이프사이클로 — "미검증 → 1차 출처 대조 → 해소"
evidence는 `verify` 플래그로 미검증 상태를 갖고, 대조 후 해소(verify 제거 / 수치 수정 / 강도 상향)된다.
- 시스템은 verify 항목을 **해소 주체로 분류**해야: 에이전트 자율(공시·뉴스·시장보고서처럼 공개 웹에 1차 출처 존재) / 사용자만(인터랙티브 재현 — KIPRIS 검색식, 사내·비공개 데이터) / 시점 의존(시총처럼 매번 달라짐).
- 에이전트 자동 검증 패스 + 인앱 사용자 해소(#3) 둘 다 필요.
- 경계: 어느 쪽이 해소 가능한지는 **출처 유형**에 달렸다. 데이터에 "누가 해소 가능한가"를 표시하면 자동/수동 라우팅이 쉬워진다.

### 2. "에이전트 조사·주입"을 1급 상호작용으로
콘텐츠 단계의 핵심 상호작용은 에이전트가 웹으로 근거·데이터를 찾아 `{ stat, source, url, grade }`로 제안 → 사용자 확인 → 주입하는 반복이다.
- 시스템은 "이 슬라이드 근거 보강해줘 / 검증해줘"를 재현 가능한 워크플로로 제공.
- 경계: 에이전트는 **제안까지**, 확정은 사용자. 임의로 confirm 하지 않는다(Discovery의 generate-then-react와 동일 철학).

### 3. 정직성 우선 — 못 맞추면 정정, 부풀리지 않기
1차 출처로 확증 안 되는 수치는 거짓 단정 대신 정직하게 정정한다(예: 단일 "209억$" → 출처 있는 범위 "$14~22B"). 강도는 추정하지 말고 명시하며 weak는 weak로 둔다(비대칭 전략).
- 시스템은 "출처 없음/불일치"를 숨기지 말고 표면화. 검증으로 약점이 드러나면 그게 산출물이다.

### 4. 시점 의존 사실(temporal facts) 처리
시총·구독자 수처럼 변하는 값은 "as-of 날짜"를 데이터에 박고, 발표 시점에 staleness를 드러내는 장치가 필요하다(예: `verifiedAt` + 오래되면 재확인 큐). 한 번 검증해도 영구 참이 아니다.
- 경계: 모든 사실이 시점 의존은 아니다. 공시·통계처럼 고정된 값과 구분해 라벨링.

### 5. 자산 라이프사이클·라이선스 — status 3개로는 부족
`check` 상태가 실제로는 세 가지로 갈렸다: (a) 데이터 확정·작도만 남음 (b) 출처/라이선스 미확정 (c) 실물 자산 부재(촬영·스톡 구매 필요).
- 더 세분화된 자산 상태 + **라이선스 추적**(아이콘셋·스톡·공공데이터 이용약관)을 고려. `have`의 의미("만들 수 있음" vs "이미 만들어짐")도 정의 필요.

### 6. 데이터 확보와 작도(렌더)는 분리된 산출물
차트 자산은 콘텐츠 단계(입력 데이터셋 확보)와 빌드 단계(Phase 4~5 작도)가 분리된다.
- 콘텐츠 산출물은 "차트 입력 데이터셋"까지여야 하고, 작도는 다음 단계. 시스템은 data-ready와 render-ready를 다른 상태로 둔다.

### 7. 단계 전환 게이트의 일반화
content→design 게이트(본문 완료 + 자산 확보 + 미검증 0)는 모든 세션에 재사용된다.
- 게이트는 진행을 막는 장치가 아니라 "무엇이 남았는지"를 보여주는 체크리스트 + 사용자 명시 승인 전환(파이프라인 공통 철학).

### 8. 검증 출처(provenance)의 구조화
현재 `verify`는 free-text 지시문이다. 시스템 단계에선 `verifiedBy` / `verifiedAt` / `method`(웹·공시·재현) 같은 구조화를 고려 — 누가·언제·어떻게 확인했는지 감사 가능하게.

### 9. 조달 주체 분류와 준비도 자동 전파 (자산·근거 공통)
파일럿에서 자산·근거가 "에이전트가 찾/만들 수 있는 것"과 "사람만 가능한 것"으로 명확히 갈렸다.
- **에이전트 가능**: 공개 데이터로 그릴 차트, 웹에서 찾을 근거, 범위 중 발표용 단일 수치 제안.
- **사람만 가능**: 실물 사진·독점 영상(촬영/스톡), 사내·비공개 데이터, 라이선스·아이콘셋 결정, 시점 의존 값의 발표 직전 재확인.
- 시스템은 각 항목에 "조달 주체"를 달아 **에이전트 작업 큐 / 사용자 요청 큐로 라우팅**하고, 의존성이 풀리면 준비도를 **자동 전파**해야 한다(예: 근거 수치가 확정되면 그 수치 기반 차트 자산이 data-ready로 자동 승격).
- 경계: "에이전트 가능"도 최종 확정은 사용자 몫(제안까지). 자동 전파가 사용자 확인을 건너뛰지 않게.

### 10. 단일 수치 선택과 근거 보강을 별도 작업으로
검증(사실 대조)과 구분되는 두 콘텐츠 결정이 있다.
- **단일 수치 선택**: 출처가 범위를 줄 때(예: 시장 규모가 기관별로 편차) 발표용 하나의 숫자를 고르는 일. 에이전트가 후보·근거를 제시하고 사용자가 고른다 — 검증과 별개의 결정.
- **근거 보강 패스**: 약한 pillar를 에이전트가 추가 사례·통계로 강화 시도(비대칭 전략의 실행). 보강에 실패하면 약함을 정직하게 유지하고, 무게중심은 강한 근거로.
- 경계: 보강은 "약점 가리기"가 아니다. 못 채우면 그대로 두고 설계에서 비중을 낮춘다.

## 과적합 경계

- 이 관찰은 **데이터 기반 비교 발표** 한 건에서 나왔다. 비전·제안형 발표는 검증·자산의 비중이 다르다.
- 자산 종류 분포(차트·도식·사진·아이콘)가 주제 특수적이다. 일반 자산 분류는 더 넓게 봐야 한다.
- "에이전트 자율 검증 4/8"은 출처가 마침 공개 웹에 있었기 때문이다. 사내·비공개 데이터 비중이 높으면 자동화율이 떨어진다.
- 워크벤치의 게이트 기준(미검증 0 등)은 이 파일럿의 임시값이다. 발표 유형별로 게이트 조건은 달라질 수 있다.
