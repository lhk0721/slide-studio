# Deck Discovery — 주제·목표 명확화 단계 명세

발표자료 제작 파이프라인의 **1단계(Discovery)** 규칙. 사용자와 LLM의 반복 대화로 주제와 목표를 명확히 하고, 그 부산물로 메시지와 스토리라인을 도출한다. 이 문서는 `/new-deck` discovery 에이전트가 따르는 "헌법"이다.

## Document Relations

- Parent: `docs/agent-workflow/README.md`
- 인사이트 참고(사례 관찰, 규칙 아님): `docs/agent-workflow/deck-discovery-insights.md`
- 산출물: `docs/sessions/<id>/brief.md` (이 단계의 Deck Brief), `docs/sessions/<id>/README.md` 요약 갱신
- 다음 단계 핸드오프: outline → `app/src/sessions/<id>/` 슬라이드 stub scaffold
- 슬라이드 작성 규칙: `docs/agent-workflow/slides-jsx-convention.md`

## 핵심 원리

> 모든 대화는 **단일 산출물 Deck Brief의 빈 슬롯을 채우는 행위**다. 슬롯이 차면 구조/스토리라인은 Brief에서 **생성**된다. 인터뷰는 구조를 따로 만들지 않는다 — 명확화의 결정론적 부산물로 구조가 나온다.

이 단계의 "자동화"는 사람을 빼는 게 아니라, **매번 즉흥적으로 잘 묻기**를 재현 가능한 에이전트 + 산출물로 시스템화하는 것이다.

## 1. Deck Brief — 슬롯 스키마

에이전트는 아래 슬롯을 점진적으로 채운다. 각 슬롯은 상태를 가진다: `비어있음` → `추정`(LLM이 채우고 확인 대기) → `확정`(사용자 확인).

| # | slot | 끌어내는 핵심 질문(예) | 필수 |
| --- | --- | --- | --- |
| 1 | `occasion` | 어떤 자리에서, 언제, 몇 분 발표? | ✅ |
| 2 | `audience` | 듣는 사람 한 명을 떠올리면 누구? 그가 이미 아는 것 / 결정 권한은? | ✅ |
| 3 | `desired_action` | 발표 직후 그 사람이 **할 단 하나의 행동**은? | ✅ |
| 4 | `core_message` | 딱 한 문장만 기억된다면 그 문장은? (spine) | ✅ |
| 5 | `pillars` | 그 주장을 믿게 만드는 근거 3~5개 | ✅ |
| 6 | `evidence` | 각 pillar의 데이터·사례·이미지 (있는 것 / 필요한 것) | ○ |
| 7 | `constraints` | 톤, 브랜드, 반드시 포함/금지, 분량 한계 | ○ |
| 8 | `deck_type` | pitch / explainer / report / proposal → 스토리라인 archetype | ✅ |
| → | `storyline` | (1~8에서 **생성**) 슬라이드별 한 줄 outline | 파생 |

- 필수 슬롯이 모두 `확정`이 되기 전에는 outline 생성으로 넘어가지 않는다.
- `추정`으로 채운 슬롯은 outline 확정 전에 반드시 사용자 확인을 받는다.

## 2. 인터뷰 규율 (과하게 주도하지 않으면서 끌어내기)

체크 가능한 행동 규칙으로 고정한다.

- **한 번에 한 질문**(많아야 2개). 질문 폭탄 금지.
- **깔때기 순서**: 넓게(주제/왜) → 좁게. 위 슬롯 번호 순서가 곧 깔때기 기본값. 단, 사용자가 앞서 말하면 순서를 건너뛰어 따라간다.
- **매 턴 미러링**: 답을 들으면 *"내가 이해한 건 X인데 맞아?"* 로 되비춘다. 사용자가 자기 생각이 정리되는 걸 보게 하는 것이 이 단계의 핵심 메커니즘이다.
- **결론이 아니라 선택지**: 사용자가 막연하면 *"A쪽이야 B쪽이야?"* 처럼 **반응할 거리**를 준다. LLM이 대신 정하지 않는다.
- **'왜' 사다리**: 표면 주제 뒤의 진짜 목표까지 2~3회 "왜?"로 내려간다.
- **충돌 들추기**: 답이 모순되면(예: 투자 유치 ↔ 교육) 그 긴장을 이름 붙이고 **우선순위를 강제**한다. 진짜 목표는 보통 여기서 드러난다.
- **위임 허용**: 사용자가 "그건 네가 정해"라고 하면 `추정`으로 채우고 나중에 확인받는다. 임의로 `확정`하지 않는다.
- **발화 비율**: discovery 동안 LLM 발화량 < 사용자 발화량. LLM은 주로 질문 + 짧은 미러.
- **사용자 언어로 되돌려준다**: Brief에는 사용자가 확인한 표현만 들어간다. LLM이 지어낸 문장을 사용자 확인 없이 확정하지 않는다.

### 슬롯별 비유도성(non-leading) 질문 뱅크

- `occasion`: "어떤 자리예요? 시간은 얼마나 있어요?" / "발표 환경은 — 무대 발표예요, 자료만 도는 거예요?"
- `audience`: "딱 한 사람이 듣는다면 누구를 상상해요?" / "그 사람이 이미 알고 있는 건? 모르는 건?" / "그 사람한테 결정 권한이 있어요?"
- `desired_action`: "발표가 끝나고 그 사람이 **무엇을 하면** 성공이에요?" / "'알게 된다' 말고 '하게 된다'로 바꾸면?"
- `core_message`: "한 문장만 남는다면? '___는 ___다' 형태로." / "그 문장에 동의 안 하는 사람은 왜 반대할까요?"
- `pillars`: "그 한 문장을 믿게 만드는 이유 3개만." / "그중 하나만 빼면 가장 약해지는 건?"
- `evidence`: "그 근거를 뒷받침할 숫자나 사례가 있어요? 없으면 뭐가 필요해요?"
- `constraints`: "톤은 — 신뢰감? 도전적? 따뜻함?" / "반드시 들어가야 할 / 절대 빼야 할 게 있어요?"
- `deck_type`: (보통 1~5에서 자동 추론. 확인만) "이건 설득(투자/제안)에 가까워요, 설명(교육/보고)에 가까워요?"

## 3. 스토리라인 Archetype

`deck_type`이 정해지면 아래 골격에 `pillars`를 매핑해 outline 초안을 생성한다. 골격은 출발점이며, 사용자가 반응해 수정한다.

- **pitch** (투자/파트너십): 훅·문제 → 솔루션 → 시장·가치 → 비즈니스 모델 → Why Now → 경쟁·차별 → 팀 → 요청
- **explainer** (교육/개념설명): 큰그림(왜 중요) → 핵심 개념 분해 → 구성요소 → 상호작용·흐름 → 구체 예시 → 흔한 오해·주의 → 정리·다음 단계
- **report** (보고/현황): 결론 먼저(요지) → 배경·지표 → 분석 → 시사점 → 액션·요청
- **proposal** (제안/설득): 현재 문제 → 제안 개요 → 근거·기대효과 → 실행안·리스크 → 비용·일정 → 요청

### Storyline 생성 규칙

- archetype 골격의 각 단계에 관련 `pillar`를 배정한다. pillar가 많은 단계는 슬라이드를 분할한다.
- **슬라이드 1장 = 메시지 1개.** 각 슬라이드 제목은 "그 슬라이드가 증명할 주장 1문장"으로 쓴다.
- 슬라이드 수는 `occasion`의 시간 제한에서 역산한다(대략 1슬라이드 ≈ 1~2분).
- 제목만 위에서 아래로 읽었을 때 그 자체로 스토리가 되면 통과. 아니면 재배치.

## 4. 상태기계 & 핸드오프

```
discovery(슬롯 채우기) → brief 확정 → outline 생성 → outline 확정 → scaffold
```

- 각 화살표는 **사용자 명시 승인**으로만 넘어간다(슬라이드 워크플로의 Pre-Commit Gate와 동일 철학).
- **수렴 신호**: 미러링 2회 연속으로 사용자가 수정 없이 확인 → 그 슬롯 `확정`. 모든 필수 슬롯 `확정` + outline 승인 → 단계 종료.
- **종료 시 산출**:
  1. `docs/sessions/<id>/brief.md` 작성/갱신 (아래 템플릿).
  2. `docs/sessions/<id>/README.md`의 청중·목적·메시지 아크·슬라이드 표 갱신.
  3. (승인 시) `scaffold`: outline → `app/src/sessions/<id>/slides/` 에 슬라이드별 placeholder `SlideNN.jsx`(제목 미리 채움) + `index.js`, `app/src/sessions/index.js` 등록.
- 이 단계의 파일 변경도 `docs/issues/`의 관리 문서에 커밋 단위로 기록한다(`documentation-rules.md`).

## 5. Brief 프론트매터 스키마 (다운스트림 파싱용)

```yaml
---
session_id: <id>
deck_type: pitch | explainer | report | proposal
occasion: <한 줄>
duration_min: <정수>
audience: <한 줄 persona>
desired_action: <발표 후 청중의 단일 행동>
core_message: <한 문장 spine>
pillars:
  - <근거 1>
  - <근거 2>
  - <근거 3>
constraints: <톤/필수/금지/분량>
status: discovery | brief-confirmed | outline-confirmed | scaffolded
---
```

## 6. brief.md 템플릿

```md
---
(위 프론트매터)
---

# Deck Brief: <세션 제목>

## 한 문장 (spine)
<core_message>

## 청중 / 원하는 행동
- 청중: <audience>
- 발표 후 행동: <desired_action>
- 자리/분량: <occasion>, <duration_min>분

## 근거 (pillars)
1. <pillar> — 증거: <evidence 또는 '필요'>
2. ...

## 제약
- <constraints>

## 스토리라인 (생성 → 확정)
| # | 슬라이드 제목(= 증명할 주장) | 매핑 pillar | 상태 |
| --- | --- | --- | --- |
| 1 | ... | ... | 초안 |

## 미해결 / 확인 필요
- <추정으로 남은 슬롯, 부족한 증거 등>
```
